# temporal-protobuf-es

## Purpose

`temporal-protobuf-es` is a community-maintained Temporal TypeScript SDK integration for payloads generated by `@bufbuild/protobuf` v2.

The package should make `protobuf-es` messages work naturally with Temporal TypeScript clients, workers, tests, and workflow bundles while preserving wire compatibility with Temporal's existing protobuf payload conventions.

This package is intentionally external to `temporalio/sdk-typescript`. It should live near the `nu-sync` Temporal code generation projects so the converter, generated schema conventions, examples, and cross-language compatibility behavior can evolve together.

## Package Identity

- GitHub repository: `nu-sync/temporal-protobuf-es`
- npm package: `@nu-sync/temporal-protobuf-es`
- Primary registry: npm
- Initial publishing command: `npm publish --access public`
- Future optional registry: JSR, after the npm package is stable and the Node install experience is understood

The package name should remain scoped under `@nu-sync` to avoid implying that this is an official Temporal package.

## Publishing Recommendation

Publish to npm first because the main consumers are applications using the Temporal TypeScript SDK, which already depend on npm packages and usually configure converters through Node resolution.

JSR can be considered later, but it should not be the first publishing target. JSR's Node support goes through its npm compatibility layer, and Temporal applications may need CommonJS or `require.resolve(...)` compatibility for `payloadConverterPath`.

## Public API

The package should expose the generic converter building blocks:

- `ProtobufEsBinaryPayloadConverter`
- `ProtobufEsJsonPayloadConverter`
- `DefaultPayloadConverterWithProtobufsEs`
- `ProtobufEsRegistryInput`

It should also expose a small helper for the common case:

```ts
import { makeProtobufEsPayloadConverter } from '@nu-sync/temporal-protobuf-es';
import { StartOrderRequestSchema, StartOrderResultSchema } from './gen/messages_pb';

export const payloadConverter = makeProtobufEsPayloadConverter([
  StartOrderRequestSchema,
  StartOrderResultSchema,
]);
```

The helper should accept either:

- a `Registry` from `@bufbuild/protobuf`
- an array of generated `DescMessage` schemas

## Temporal SDK Integration

Applications should create an app-local `payload-converter.ts` file because the package cannot know which generated schemas the application uses.

Example:

```ts
import { createRegistry } from '@bufbuild/protobuf';
import { DefaultPayloadConverterWithProtobufsEs } from '@nu-sync/temporal-protobuf-es';
import { StartOrderRequestSchema, StartOrderResultSchema } from './gen/messages_pb';

const registry = createRegistry(StartOrderRequestSchema, StartOrderResultSchema);

export const payloadConverter = new DefaultPayloadConverterWithProtobufsEs({
  registry,
});
```

Client usage:

```ts
import { Client } from '@temporalio/client';

const client = new Client({
  connection,
  namespace: 'default',
  dataConverter: {
    payloadConverterPath: require.resolve('./payload-converter'),
  },
});
```

Worker usage:

```ts
import { Worker } from '@temporalio/worker';

const worker = await Worker.create({
  connection,
  taskQueue: 'orders',
  workflowsPath: require.resolve('./workflows'),
  activities,
  dataConverter: {
    payloadConverterPath: require.resolve('./payload-converter'),
  },
});
```

A plugin wrapper may be added after the base converter is stable. The converter should remain the core abstraction; the plugin should only improve wiring ergonomics.

## Dependencies

Peer dependencies:

- `@bufbuild/protobuf`
- `@temporalio/common`

Development and test dependencies should include the Temporal packages needed to run integration tests:

- `@temporalio/client`
- `@temporalio/worker`
- `@temporalio/testing`

The package should avoid depending on `protoc-gen-ts-temporal` directly. The generator can depend on this package, but this package should stay useful to any application that already has `protobuf-es` schemas.

## Compatibility Goals

The package should be compatible with:

- Node applications installed through npm-compatible package managers
- Temporal TypeScript SDK client and worker data converter loading
- Deno applications that consume npm packages
- Rust Temporal SDK workers or clients that exchange protobuf payloads with TypeScript

The wire format should match Temporal protobuf conventions:

- binary protobuf payloads use the `binary/protobuf` encoding marker
- JSON protobuf payloads use the `json/protobuf` encoding marker
- payload metadata includes the fully qualified protobuf message type
- binary payload bytes are compatible with the same message encoded by other protobuf runtimes
- proto3 JSON payloads follow canonical protobuf JSON behavior as implemented by `@bufbuild/protobuf`

## Test Plan

### Unit Tests

Unit tests should verify:

- `protobuf-es` message instances serialize to Temporal payloads
- binary payloads round-trip through `ProtobufEsBinaryPayloadConverter`
- JSON payloads round-trip through `ProtobufEsJsonPayloadConverter`
- the default composite converter delegates ordinary JSON, binary, and `undefined` values correctly
- missing registry entries produce useful errors
- malformed payload metadata produces useful errors
- `google.protobuf.Any` works when the registry contains embedded message schemas
- plain objects with `$typeName` are handled intentionally and documented

### npm Compatibility Tests

Create a minimal npm-installed fixture application that:

- installs `@nu-sync/temporal-protobuf-es` from the packed npm tarball
- installs `@bufbuild/protobuf` and Temporal SDK packages through npm-compatible package managers
- uses both ESM imports and the `payloadConverterPath` pattern expected by Temporal workers
- verifies `require.resolve('./payload-converter')` works where the SDK needs it
- starts a TypeScript client and worker using the converter
- passes a generated `protobuf-es` message as workflow input and receives a generated message result

Run this fixture before publishing each release.

### Deno Compatibility Tests

Create a Deno fixture that:

- imports the package through Deno's npm package support
- imports generated `protobuf-es` schemas
- constructs the payload converter
- serializes and deserializes payloads without relying on Node-only APIs
- verifies the package can be used by Deno code that starts Temporal workflows through the TypeScript SDK path that Deno supports

If full Temporal worker execution is not practical in Deno, keep the Deno test focused on converter construction and payload round trips, and document the limitation.

### Rust Compatibility Tests

Create a cross-language fixture that:

- defines a shared `.proto` file
- generates TypeScript messages with `@bufbuild/protoc-gen-es`
- generates Rust messages with `prost` or the generator used by `protoc-gen-rust-temporal`
- encodes a TypeScript `protobuf-es` message to a Temporal payload
- decodes the payload in Rust and verifies field equality
- encodes the same Rust message to a Temporal-compatible protobuf payload
- decodes the payload in TypeScript and verifies field equality

This should cover both binary protobuf and proto3 JSON payloads where practical. Binary compatibility is the most important baseline.

### Temporal Integration Tests

Run an end-to-end test with:

- a TypeScript Temporal client
- a TypeScript Temporal worker
- generated `protobuf-es` workflow input and output messages
- the app-local `payload-converter.ts` module
- workflow start, signal, query, update, and activity arguments where possible

Run a second end-to-end compatibility scenario with:

- a TypeScript Temporal client
- a Rust Temporal worker
- a shared `.proto` workflow argument message
- the TypeScript converter producing payloads that the Rust worker can decode

## Release Criteria

Before the first public release:

- the npm package installs cleanly from `npm pack`
- the package exports work in at least one ESM Node fixture
- the Temporal `payloadConverterPath` fixture works
- the Deno converter fixture passes
- the Rust binary payload compatibility fixture passes
- README usage examples are copied from tested fixtures
- peer dependency ranges are explicit
- the package is marked as community-maintained and not official Temporal SDK code

## Open Questions

- Should the package ship a Temporal `SimplePlugin` wrapper, a custom plugin class, or only converter helpers for the first release?
- Should the package support CommonJS directly, or only expose ESM plus a documented app-local CommonJS converter file pattern?
- Should `protoc-gen-ts-temporal` generate the app-local `payload-converter.ts` file automatically?
- Should JSON protobuf compatibility be considered a required cross-language guarantee, or should binary protobuf be the primary supported path?
